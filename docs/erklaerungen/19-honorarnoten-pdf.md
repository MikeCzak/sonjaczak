## 1. PHP-Extensions

### Was eine Extension ist

PHP selbst ist ein Programm in C. Vieles, was in PHP wie eingebaut aussieht, steckt in **Extensions**: in C
geschriebene Module, die Funktionen und Klassen bereitstellen. `DOMDocument` kommt aus der Extension `dom`,
`mb_strlen()` aus `mbstring`, `ZipArchive` aus `zip`, der Datenbanktreiber aus `pdo_pgsql`. Fehlt eine Extension, gibt es
die Klasse oder Funktion schlicht nicht („Call to undefined function“).

Eine Extension kann auf zwei Arten in PHP landen:

- **Fest einkompiliert** (statisch): beim Bauen von PHP mitgebaut, immer da, nicht abschaltbar.
- **Als eigene Datei** (shared, `.so`): wird nur geladen, wenn eine ini-Datei sie mit `extension=…` nennt.

Im Container sieht man das so (geprüft 2026-11-17):

```bash
docker compose exec php php -m                     # alle geladenen Extensions
docker compose exec php sh -c 'ls $PHP_INI_DIR/conf.d/'
```

In `conf.d/` liegen `docker-php-ext-apcu.ini`, `-intl`, `-pdo_pgsql`, `-sodium`, `-xdebug`, `-zip`: Das sind die
nachgeladenen. `dom`, `mbstring`, `xml`, `ctype` usw. stehen in `php -m`, haben aber keine ini-Datei, sind also im
Basis-Image fest einkompiliert. Was dazukommt, installiert unser `Dockerfile` mit `install-php-extensions` (Zeile für
Zeile in `02-dockerfile.md`); das Skript baut die Extension, legt die ini-Datei an und räumt die Build-Werkzeuge weg.

Jede Extension macht das Image größer und kann Systembibliotheken mitbringen (GD etwa libpng, libjpeg, freetype).
Deshalb nur, was gebraucht wird.

### Wie Composer Extensions prüft

Pakete nennen ihre Extensions in `require` als `ext-name`, z. B. `"ext-dom": "*"`. Das sind keine Pakete zum
Herunterladen, sondern **Plattform-Pakete**: Composer prüft, ob die Extension in dem PHP vorhanden ist, mit dem Composer
läuft. Fehlt sie, bricht `composer install` ab. Bei uns läuft Composer im Container und beim Image-Bau in der CI;
eine fehlende Extension fällt also spätestens beim Build auf, nicht erst in Produktion.

Zur Laufzeit prüft Composer dagegen nur die PHP-Version: `vendor/composer/platform_check.php` enthält nur die Zeile zu
PHP ≥ 8.5.12, weil `platform-check` auf dem Standard `php-only` steht (`composer config platform-check` im Container).
Wer Extensions im Code optional nutzt, prüft selbst (`extension_loaded()`).

### Was dompdf braucht

Aus `vendor/dompdf/dompdf/composer.json` (3.1.6) und dem README, Abschnitt „Requirements“:

| Extension | Pflicht? | Wofür | Bei uns |
|---|---|---|---|
| `dom` | ja (`ext-dom`) | dompdf baut aus dem HTML einen DOM-Baum (über `masterminds/html5`) und rechnet darauf das Layout | einkompiliert |
| `mbstring` | ja (`ext-mbstring`) | Zeichenketten mit Mehrbyte-Zeichen: ä, ß, € sind in UTF-8 mehrere Bytes | einkompiliert |
| `gd` | nein, „for image processing“ | Bilder im PDF (PNG, JPEG) | **nicht installiert** (`extension_loaded('gd')` = false) |
| `imagick` / `gmagick` | nein | schnellere Bildverarbeitung für manche Formate | nicht installiert |

Die Honorarnote hat keine Bilder (keine Unterschrift, kein Logo), daher kein GD. Kommt später ein Logo dazu, muss
`gd` in die Liste von `install-php-extensions` im `Dockerfile` (wie dompdf ohne GD auf ein Bild reagiert, ist nicht
geprüft). Für den ZIP-Download (D2d) nutzen wir `ZipArchive` aus `zip`, das schon für Composer im Image ist.

Die übrigen Abhängigkeiten sind PHP-Pakete, keine Extensions (`composer.lock`): `dompdf/php-font-lib` 1.0.2 (liest
Schriftdateien), `dompdf/php-svg-lib` 1.0.2 (SVG), `masterminds/html5` 2.12.0 (HTML5-Parser),
`sabberworm/php-css-parser` 9.5.0 (CSS).

Ein Symfony-Rezept gibt es für dompdf nicht; was das bedeutet: `04-composer.md`, „Wenn es kein Rezept gibt“.

## 2. Die Migration Zeile für Zeile

`src/Migrations/Version20261117063716.php`, erzeugt mit `doctrine:migrations:diff` aus `src/Entity/InvoicePdf.php`:

```sql
CREATE TABLE invoice_pdf (id INT GENERATED BY DEFAULT AS IDENTITY NOT NULL, content BYTEA NOT NULL,
    invoice_id INT NOT NULL, PRIMARY KEY (id));
CREATE UNIQUE INDEX UNIQ_A601B44F2989F1FD ON invoice_pdf (invoice_id);
ALTER TABLE invoice_pdf ADD CONSTRAINT FK_A601B44F2989F1FD FOREIGN KEY (invoice_id) REFERENCES invoice (id)
    NOT DEFERRABLE;
```

### `GENERATED BY DEFAULT AS IDENTITY NOT NULL`

Eine **Identity-Spalte** ist PostgreSQLs Standard-SQL-Weg für fortlaufende IDs (früher `SERIAL`). Laut Doku hängt
PostgreSQL eine Sequenz an die Spalte, und neue Zeilen bekommen ihren Wert daraus; die Spalte ist „implicitly
`NOT NULL`“. Das `NOT NULL` in der Migration ist also doppelt, schadet aber nicht (Doctrine schreibt es für jede
Spalte ohne `nullable` hin). Woher Doctrine `IDENTITY` nimmt: `09-datenbank-schueler.md`, „Identity statt Sequence“.

**`BY DEFAULT` oder `ALWAYS`** (Doku, wörtlich): Bei `INSERT` mit `ALWAYS` wird ein selbst angegebener Wert nur mit
`OVERRIDING SYSTEM VALUE` angenommen, bei `BY DEFAULT` „the user-specified value takes precedence“. Bei `UPDATE` lehnt
`ALWAYS` jeden Wert außer `DEFAULT` ab, `BY DEFAULT` erlaubt das Ändern. `BY DEFAULT` ist nachgiebiger: Ein Import oder
ein Test darf eine ID vorgeben. Fallstrick dabei: Die Sequenz merkt das nicht. Wird `id = 100` von Hand eingefügt,
vergibt die Sequenz später irgendwann selbst die 100, und der Insert scheitert am Primärschlüssel.

**Lücken sind normal.** Eine Sequenz gibt einen Wert auch bei einem Rollback nicht zurück. Versuch in der lokalen
Datenbank (temporäre Tabelle):

```sql
INSERT INTO t (v) VALUES ('a');                       -- id 1
BEGIN; INSERT INTO t (v) VALUES ('b'); ROLLBACK;      -- verbraucht id 2
INSERT INTO t (v) VALUES ('c');                       -- id 3
INSERT INTO t (id, v) VALUES (100, 'explizit');       -- BY DEFAULT: angenommen
-- Ergebnis: 1, 3, 100
```

Für technische IDs egal. Genau deshalb kommt die **Nummer der Honorarnote** nicht aus einer Sequenz, sondern aus
`MAX(number) + 1` unter dem Advisory Lock (`13-honorarnoten.md`, `15-sperren.md`): Scheitert das PDF (D2b, Option A),
rollt alles zurück, und die nächste Honorarnote bekommt dieselbe Nummer. Die `id` der Honorarnote hat dann eine Lücke,
die Nummer nicht.

### `content BYTEA NOT NULL`

`bytea` ist PostgreSQLs Typ für beliebige Bytes. Doctrines Typ `blob` wird auf PostgreSQL dazu. Fallstrick: Beim Laden
liefert Doctrine einen Stream statt eines Strings (`vendor/doctrine/dbal/src/Types/BlobType.php`, „maps an SQL BLOB to a
PHP resource stream“); `InvoicePdf::getContent()` liest ihn einmal aus. PHPStan fand dabei eine Typlücke: Ein
geschlossener Stream besteht `is_resource()` nicht mehr, daher prüft der Code `!is_string()`.

### Unique-Index auf `invoice_id`

Eine 1:1-Beziehung ist in der Datenbank eine n:1-Beziehung mit Unique-Index (wie `student.user_id`,
`09-datenbank-schueler.md`). Doctrine legt ihn bei `OneToOne` selbst an. Ohne ihn könnten zwei PDFs an einer
Honorarnote hängen. Der Name `UNIQ_…` ist ein Hash aus Tabelle und Spalte, von Doctrine erzeugt.

**Warum `Invoice` sein PDF nicht kennt:** Die Seite einer 1:1-Beziehung ohne Fremdschlüssel (die inverse Seite) lädt
Doctrine nie lazy (`vendor/doctrine/orm/src/UnitOfWork.php`, Kommentar „Inverse side of x-to-one can never be lazy“). Ein
Feld `Invoice::$pdf` hieße: Jede Liste von Honorarnoten lädt alle PDFs mit, und die eigene Tabelle wäre umsonst. Daher
nur `InvoicePdf::$invoice`, gelesen über `InvoicePdfRepository::findForInvoice()`.

Verworfen: die Honorarnote als Primärschlüssel von `InvoicePdf` („shared primary key“, keine eigene `id`). Spart eine
Spalte, aber das PDF bräuchte beim Speichern schon die ID der Honorarnote, die erst beim selben Flush entsteht; ob
Doctrine das in einem Flush auflöst, ist nicht ausprobiert. Die eigene `id` hat dieses Risiko nicht.

### `FOREIGN KEY … NOT DEFERRABLE`

Ein Fremdschlüssel wird geprüft, wann immer eine Zeile eingefügt, geändert oder gelöscht wird. Die Frage ist nur,
**wann** innerhalb einer Transaktion. PostgreSQL-Doku (Abschnitt `DEFERRABLE`/`NOT DEFERRABLE`, sinngemäß, beim Abruf
nicht wörtlich vorliegend):

- **`NOT DEFERRABLE`** (Standard): Die Bedingung wird **sofort nach jedem Befehl** geprüft. Ein `INSERT` in
  `invoice_pdf` mit einer `invoice_id`, die es (noch) nicht gibt, scheitert sofort.
- **`DEFERRABLE INITIALLY IMMEDIATE`**: auch nach jedem Befehl geprüft, aber eine Transaktion darf mit
  `SET CONSTRAINTS … DEFERRED` auf „am Ende prüfen“ umschalten.
- **`DEFERRABLE INITIALLY DEFERRED`**: erst beim `COMMIT` geprüft. Zwischendurch darf die Datenbank inkonsistent sein,
  nur am Ende nicht. Nützlich bei Kreisbezügen (A zeigt auf B, B auf A), die sich sonst nicht einfügen lassen.
- Aufschiebbar sind nur `UNIQUE`, `PRIMARY KEY`, `EXCLUDE` und Fremdschlüssel; `NOT NULL` und `CHECK` nie.

Das `NOT DEFERRABLE` in der Migration ist also der Standard, nur ausdrücklich hingeschrieben: Doctrine DBAL behandelt
jeden Fremdschlüssel ohne Option `deferrable` als „nicht aufschiebbar“ (`vendor/doctrine/dbal/src/Schema/
ForeignKeyConstraint.php`, `parseDeferrability()`: „a constraint is NOT DEFERRABLE unless explicitly declared …“) und
schreibt das ins SQL. Für uns passt das: Doctrine sortiert die Inserts beim Flush selbst so, dass erst `invoice`, dann
`invoice_pdf` eingefügt wird. Ein Fehler würde so sofort beim falschen Befehl auffallen statt erst beim Commit.

Ohne `ON DELETE`: Löschen einer Honorarnote mit PDF verweigert die Datenbank (`NO ACTION`, wie überall im Projekt,
`09-datenbank-schueler.md`). Honorarnoten werden ohnehin nie gelöscht.
