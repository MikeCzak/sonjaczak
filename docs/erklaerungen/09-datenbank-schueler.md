## Was in der Datenbank entsteht

```sql
CREATE TABLE guardian (id INT GENERATED BY DEFAULT AS IDENTITY, name VARCHAR(200) NOT NULL, email …, phone …,
    address_street …, address_postal_code …, address_city …, address_country …)
CREATE TABLE student (id …, first_name …, last_name …, birth_date DATE, …, address_street …,
    guardian_id INT NULL REFERENCES guardian (id),
    user_id INT NULL UNIQUE REFERENCES app_user (id))
CREATE INDEX idx_student_name ON student (last_name, first_name)
```

- **Embeddable → Spalten mit Präfix:** `Student::$address` wird zu `address_street` usw. Keine eigene Tabelle, kein
  Join. Alle Adress-Spalten sind `NULL`-fähig, weil Doctrine ein Embeddable nie `null` lässt: Eine fehlende Adresse ist
  ein `Address`-Objekt mit leeren Feldern. Ob sie für eine Honorarnote reicht, sagt `Address::isComplete()`.
- **n:1 Student → Guardian:** Die Spalte `guardian_id` liegt in `student`, also ist `Student::$guardian` die
  **Owning Side**. `Guardian::$students` (`mappedBy: 'guardian'`) ist die **Inverse Side**, nur zum Lesen.
  Fallstrick: `$guardian->getStudents()->add($student)` ändert in der Datenbank nichts. Zuordnen immer mit
  `$student->setGuardian($guardian)`. (Darum gibt es in `Guardian` kein `addStudent()`.)
- **1:1 Student → User:** Owning Side ist `Student` (Spalte `user_id`, `UNIQUE`). Eine 1:1-Beziehung ist in der
  Datenbank eine n:1 mit Unique-Index; ohne `unique` könnten zwei Schüler:innen dasselbe Konto haben. Wird erst mit
  `ROLE_STUDENT` benutzt.
- **Kein `ON DELETE`:** Doctrine schreibt ohne `onDelete` keine Klausel; PostgreSQL nimmt dann `NO ACTION` und
  verweigert das Löschen eines Elternteils, solange Schüler:innen auf ihn zeigen. Das ist gewollt (`datenmodell.md` 5:
  keine Kaskaden). Der Controller prüft vorher selbst und zeigt eine verständliche Meldung statt eines
  Datenbankfehlers.
- **Index auf (Nachname, Vorname):** für die sortierte Liste. Bei ein paar Dutzend Zeilen merkt man ihn nicht; er
  kostet aber auch nichts und passt zur Sortierung.
- **Identity statt Sequence:** `GENERATED BY DEFAULT AS IDENTITY` kommt aus `identity_generation_preferences` in
  `config/packages/doctrine.yaml` (Standard des Doctrine-Rezepts für PostgreSQL).

## Formulare: zwei Fallstricke

- **`empty_data => ''` bei Pflicht-Strings:** Ein leeres Textfeld liefert sonst `null`, und `setFirstName(string)`
  wirft einen TypeError, bevor die Validierung („darf nicht leer sein“) überhaupt läuft. Mit `empty_data` = `''` hängt
  `TextType` einen Transformer an, der `null` zu `''` macht (`vendor/symfony/form/Extension/Core/Type/TextType.php`).
  Für Felder, die `null` sein dürfen (E-Mail, Telefon), ist `null` richtig.
- **`empty_data` bei Klassen mit Konstruktor-Argumenten oder Embeddables:** `AddressType` erzeugt sein Objekt selbst,
  damit nie `null` in `setAddress()` landet.

## Suche

`StudentRepository::search()` sucht in Vor-, Nachname und Name des Elternteils, ohne Groß-/Kleinschreibung. DQL kennt
kein `ILIKE`, deshalb `LOWER(...) LIKE :term` mit kleingeschriebenem Suchbegriff. `%` und `_` sind in `LIKE`
Platzhalter und werden mit Backslash maskiert (PostgreSQLs Standard-Escape-Zeichen). Der Elternteil wird gleich
mitgeladen (`addSelect('g')`), sonst gäbe es in der Liste eine Abfrage pro Zeile („N+1-Problem“).

## Löschen und der StudentVoter

`StudentVoter::DELETE` entscheidet, ob eine Schülerin gelöscht werden darf. Heute immer ja (für `ROLE_ADMIN`). Ab D1
(Honorarnoten) kommt die Regel „nicht mit Honorarnoten“ dazu, weil Belege aufbewahrt werden müssen. Templates und
Controller fragen schon jetzt den Voter, damit sich dort später nichts ändert.

Das Löschen braucht einen zweiten Klick (`<details>` in `templates/admin/_delete.html.twig`), ohne JavaScript.

## Alternativen

- **Eigene Tabelle `address`** statt Embeddable: lohnt sich, wenn Adressen geteilt oder unabhängig verwaltet werden.
  Hier gehört jede Adresse zu genau einer Person.
- **Zwei Elternteile als zwei Guardians** (n:m): genauer, aber auf der Honorarnote steht ohnehin ein Text wie „Anna
  und Peter Muster“. Ein Namensfeld reicht (Entscheidung in `datenmodell.md` 3.2).
- **Autocomplete statt Auswahlliste** für den Elternteil (Symfony UX Autocomplete): erst sinnvoll bei vielen
  Einträgen; die UX-Entscheidung ist ohnehin offen (C4).

## Sicherheit und DSGVO

- Alles unter `/admin`, `ROLE_ADMIN` doppelt: `access_control` und `#[IsGranted]` am Controller.
- Keine Personendaten in Logs: Die Controller loggen nichts, Flash-Meldungen enthalten keine Namen.
- Lokal und in Tests nur erfundene Daten (Foundry, `de_AT`); E-Mails aus `safeEmail()` enden auf `example.*`.
- Löschen ist endgültig (keine „Papierkorb“-Spalte). Aufbewahrungsfristen für Belege betreffen Honorarnoten, nicht
  die Stammdaten allein (offen: BAO-Frist prüfen, Abschnitt F).
